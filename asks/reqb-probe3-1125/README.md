# 要望 B probe3（掲示板 #5226 の決定）

長い衣料の品切れで「作る側が増えない理由」を読むための probe。
合格/不合格の線で判定する包みではなく、詰まりを分岐順に切り分ける
「読みの手順」の包み。

## 経緯

- 案 A+B の集計（#5206）: 案 B は「記録 → 作る量の見方」までは届いたが、
  値段の見込みと計画目標には届かず、衣料の品切れ量は減らなかった。
  品切れ量の 91.1% が 3 ターン以上の続きの中にあった。
- 長期品切れの調査（#5225、記録とコード読み）: 合図は届いている
  （入の側で作る側の見方が不足を示したのは長期品切れターンの 99.4%）。
  長期品切れの姿は「全力で作っても足りない」ではなく「作っていない」
  （生産 0 か記録なしが 91.1%）。量の中心は建国直後から衣料の供給が
  立ち上がらない島（建国 10 ターン目までに始まる続きが量の 72.0%）。
  ただし判定ごとの止まり理由は記録に写っておらず未確認だった。
- #5226 の決定: #5225 の提案 1〜4 に輸入の確認 5 を足して、次の probe を作る。

## 構成

- 版: 枝 `mugi/req-b-expected-demand` @95a31939（案 A+B 実装入り。ask.json の commit）
- 6 場面（plan・none・independent・small・open・war）× 種 1 × 切/入、300 ターン、計 12 本 + report
- 種が 1 本だけなのは、36 本（種 3 本）の測定でゆらぎの幅は分かっているため
  （probe2 と同じ考え方）。切/入の差は種 1 本では ゆらぎと分けられないので、
  この包みの集計は両側に共通する「姿」を読むのが主で、差は参考に留める。
- 切/入は probe の `--off`/`--on` で config の `market.expected_demand` を
  その場で切り替える（game.yaml は触らない）。

## 記録の追加（#5226 の 1〜5）

台本は `reqb_probe3.py`。1 行 = 1 島 × 1 ターン。財ごとの項目は
probe-ab と同じ（price / demand / supply / sold / shortage / expected /
added / shortage_exp / first / placed / wanted_off / subst / unmet_first /
view_demand / view_shortage / plan_goal / production）。
exp_price と diag は落とした（#5014 の診断は #5206 で済んでいる）。

島の行に足した物:

1. **entry_block の写し**: そのターンの参入の回で建たなかったわけ
   （`economy.finance["entry_block"]` の {facility, reason, args}）。
   参入が起きた・候補が無かったターンは null。計画経済では参入自体が
   走らないので null のままになる。
   あわせて **entries_list**: そのターンに新しく建った施設の {kind, recipe}
   の並び（提案 3「参入した施設の種類」。probe-ab は件数だけだった）。
2. **chain（衣料の鎖の施設ごと記録）**: 今の作り方の産出に cotton か
   clothing を含む施設（綿畑 = farm の cotton 系、衣料工場 = textile_mill）
   ごとに、稼働率（rate。1000 が全力）、止まった理由（status の生の文字と
   stops の組 group）、雇えた人数と雇いたかった人数、原料ごとの在庫
   （stock_in）、大きさと上限、建て増しの工事の数、売り逃しの合図
   （missed_n / missed_pos / invest_signal。建て増しの判定の入口と同じ式）。
3. （提案 3 は entries_list で対応。上の 1 を参照）
4. **建国直後の分離**: 集計（report）で、品切れの「続き」を開始ターンで
   分ける（10 ターン目までに始まった続き / それ以外）。記録自体は
   1 ターン目から全部残るので、集計側で分ける。
5. **imports_clothing（輸入で埋めていたか）**: 衣料について、
   - ordered: 商社が出した輸入の買い注文の量の合計（貿易の段の
     `_import_order` を包んで戻り値の注文量だけを数える。
     fxsplit probe と同じやり方で、ゲームの挙動は変えない）
   - why / why_market: ターン終わりに商社の衣料の item に残っていた
     届かなかったわけ（注文の段 / 圏の市場の段。商社ごとの数）
   - money: そのターンに決済された衣料の輸入額（books の
     `import.clothing`。圏の市場の約定・契約の履行・海外の商人の売りが
     全部ここに入る）
   - held / transit: 商社の衣料の持ち高（運ぶ途中を含む）と輸送中の量
   - contract_qty / contract_delivered / contract_short: 衣料の買い契約の
     取り決め量、そのターンに届いた量、届かなかった量（累計の差）

## 台本で拾えなかった物（未確認）

- **建て増し（_invest）が見送られた理由そのもの**: ゲームは `_invest` の
  見送り理由をどこにも残さない。台本で肩代わりすると判定の写しを
  もう 1 つ作ることになり、本物とずれ得るのでやめた。代わりに、判定の
  入力になる状態（売り逃しの合図・施設の大きさ・建て増しの工事中か）を
  chain に残す。集計では「合図が立っていたのに工事も建て増しも無い」
  ところまでしか言えない。
- **輸入の「届いた量」の物理量**: 注文ごとの約定量は注文の物
  （Order）に書き戻されないため、注文からは追えない。決済された輸入額
  （money）と商社の持ち高・輸送中の量で代える。船の到着そのものの量は
  拾えない。
- entry_block は「そのターンの参入の回で、いちばん見込みのあった
  候補が建たなかったわけ」1 件だけ（候補ごとの全件ではない）。
  ゲーム側の持ち方がそうなっている。

## 比べ方と読みの順序（#5216 の分岐順）

report は次の順で出す。安い分岐から先に潰す。

1. **合図は判定に届いているか**（先頭の分岐）:
   コード読みの結論（#5225）— 参入（_fill）と計画の生産目標は
   view_demand を読む。建て増し（_invest）と既存工場の操業目標は
   読まない（合図は売り逃しの記録と前ターンの売れた量）。
   report は記録側の裏づけとして、衣料の品切れターンで
   view_shortage が不足を示した割合を出す。
2. **衣料工場の稼働率は天井付近か**: 長い続き（3 ターン以上）ごとに、
   衣料工場が無い / あるが天井（稼働率 900 = FULL の 9 割）に届かない /
   天井付近まで作ったことがある、に分ける。建国直後から始まった続きは
   分けて数える（工場が立つ前の話）。
3a. **天井側**: その続きの島ターンに残っていた entry_block の理由の
   内訳と、衣料工場の建て増しの合図・工事の有無。長い続きの間に
   新しく建った施設の種類も並べる。
3b. **非天井側**: 鎖の施設の止まった理由の組（inputs / workers /
   funds など）、衣料工場の綿の在庫が 0 だった割合、綿自体の
   品切れの割合。
4. **輸入で埋めていたか**: 長い続きの島ターンで、輸入の注文量・
   届かなかったわけ・決済された輸入額・契約で届いた量を合計する。
